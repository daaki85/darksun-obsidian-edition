# 2026-11-18: the mod under DOSBox-X, the game's memory in a shared file

An experiment, not a feature. The question: can the mod run under DOSBox-X with the emulated
PC's RAM kept in a file (`[dosbox] memory file=PATH`, DOSBox-X 2025.01.01 and later) that the
Loader reads and writes, instead of reading and writing another process's memory? The research
behind it is section 8 of `reports/modernisation-research-and-plan.md`; the verdict is in that
report's "DOSBox-X: what was found".

Everything here ran in a game of its own (display `:59`, its own copy of the game folder and its
own work folder), never the shared one. No quick saves or autosaves (`settings.json`), and no save
after a memory edit.

## What was used

- **DOSBox-X 2026.10.01, SDL2, Linux 64-bit**, built here from the project's source (its GitHub
  repository's default branch as of 2026-11-18; the program reports "2026.10.01 Commit f1c4414").
  Ubuntu 24.04's package is 2024.03.01, older than the memory-file option, so it was not used.
- The build: `apt-get install libsdl2-dev libfluidsynth-dev libgl-dev libxkbfile-dev libxrandr-dev
  libasound2-dev libsdl2-net-dev` (autoconf, automake, g++, libpng, freetype, ncurses were there),
  then `./autogen.sh && ./configure --enable-sdl2 && make -j4`: **361 seconds** (6 minutes) on 4
  cores. The program is 120 MB unstripped. Its `config.h` has the dynamic cores (`C_DYNAMIC_X86`,
  `C_DYNREC`), FluidSynth, MT-32 and OpenGL.
- The experiment's code, all marked experimental and none of it used by the Loader's own start:
  - `obsidian-edition/dsloader/process.py`: `FileMemory`, the memory file behind
    `ProcessMemory`'s interface (`pread`/`pwrite` on the file; no process access). With
    `DSLOADER_MEMORY_FILE` set, `dsloader.__main__.connect` uses it for every command.
  - `obsidian-edition/dsloader/dosboxx.py`: a whole DOSBox-X configuration for the mod
    (nothing stacked on GOG's) and the command line.
  - `playtest/start_dosboxx.sh DOSBOX-X [name=value ...]`: starts the mod under DOSBox-X in a
    game of its own (`PT_DISPLAY`, `PLAYTEST_WORK`), with the dice log on the file; `PT_SAVE=NAME`
    loads a save as `loadsave.sh` does.
  - `playtest/codepatch.py`: is a write to code acted on at once (experiment 5).
  - `playtest/env.sh`, `paths.py`: `PT_DISPLAY` names another display than `:55`;
    `framerate.py` reads its own game's pid (`dsun.pid`) for the CPU figure.

## 1. The unmodded game with a memory file: works

A configuration of our own (`dosboxx.py`, `dice_log=false`: `machine=svga_s3`, `memsize=32`,
`ems=false`, `cycles=fixed 20000`, `core=normal`, `memory file=...`), the game started from the
game folder with `darksun`.

- **The file is created** by DOSBox-X at start, **33,554,432 bytes** (exactly `memsize`), mode
  0600. It is sparse: about 1 MB of it is really there once the game is at its title. The log
  says "Using memory file '...' as guest memory".
- **It is the guest's RAM**: "01/01/92" at FFFF5h, the interrupt table at 0 (segments 0824h, 0070h,
  F000h), the BIOS tick at 0:046Ch going up by 18 a second. Guest address = file offset.
- **tmpfs (`/dev/shm`) and a normal folder (ext4) both work**, the same way.
- DOSBox-X makes the file again at each start: it opens it, cuts it to nothing (`ftruncate` 0),
  sets its size and maps it shared (`src/hardware/memory.cpp`). So a mapping the Loader held from
  the last run would fault if read at that moment (SIGBUS): the backend uses `pread`/`pwrite` on
  the file, which only come back short. The file is left behind when DOSBox-X closes.
- The log also says "Memory file overrides Game Link memory interface": DOSBox-X has a second,
  older way to share its memory (Game Link, shared memory with a fixed layout); not tried.
- **Two of DOSBox-X's defaults stop the game**, and are set in the configuration:
  - the Sound Blaster's IRQ is 7 by default; the game is set up for GOG's card (220h, IRQ 5,
    DMA 1, high DMA 5) and stops with "Mel Fatal Error #: 26 ... DSP Detect Fail";
  - `doublescan=true` makes the 320x200 picture a 640x480 window: `doublescan=false` with
    `aspect=true`, `scaler=none` gives 320x240 as on 0.74.

## 2. The Loader's memory through the file: works

`FileMemory` gives `guestmem.locate` one region, the file, at base 0. **`locate`'s own search
finds it unchanged** (the BIOS date, then the interrupt table) in 3 ms; `GuestMemory.read` shows
live state (the tick at 0:046Ch: 18 more a second later). No process is opened: the DOSBox-X pid
is not needed at all, except to hold the game still for the item lists' gate (`itemgate.py`
suspends the process: a signal, which needs no memory access; `DSLOADER_MEMORY_PID`).

`find_dosbox_processes` takes any process with "dosbox" in its name, so it lists `dosbox-x` too
(beside the other agents' `dosbox` here): with the memory file named, the Loader never asks.

## 3. The helper under DOSBox-X: loads high, in the HMA, the game runs

Started as the Loader starts it: the patched copy, `d:\umbplus.com`, `lh d:\dsclog.exe`,
`d:\dsunlog.exe`. "DSCLOG loaded." The save `pens-after-arena` loaded through the kit
(`PT_SAVE`), the party walked, the mod's drawing is there. `buildcheck.py` (through the file):
every routine the same as the EXE, 134 vectors at their handlers, the tail's data the same: OK.
"Out of memory in OEOpenGraph" never appeared (the map open in every run).

`memaudit.py` in the slave pens with the map open, DOSBox 0.74 (my own copy of Ubuntu's
0.74-3, run as `db74` on the same display, the Loader's usual configuration) beside DOSBox-X:

| | 0.74 with the mod | DOSBox-X, its defaults and `dos=umb` | DOSBox-X, the configuration kept |
|---|---|---|---|
| the game's load segment | 01A2h | 0824h | **0224h** |
| free after the game, map open | 99,008 bytes | 72,352 bytes | 96,928 bytes (2,080 less than 0.74) |
| upper memory | C900h-F000h (UMBPLUS), 156 KB | CC00h-F000h, 144 KB | the same |
| the helper | C90Bh, loaded high | CC4Bh, loaded high | the same |
| the game's overlay buffer | DA4Bh | DD8Bh | the same |
| see-through tables, music buffer | E99Bh, ED11h | E99Bh, ED11h | the same |
| free upper memory | 144 and 29,696 bytes | 1,168 and 16,384 bytes | the same |
| the far block | the HMA (`far_seg` FFFFh) | the HMA | the HMA |

- **Conventional memory.** By default DOSBox-X keeps DOS's own structures in the 640 KB and pads
  them up to segment 0700h (`minimum mcb free`), so the game loads 26,656 bytes higher than on
  0.74 and has that much less. `[dos] minimum mcb free=100` alone: load segment 0574h.
  With `kernel allocation in umb=true` as well: **0224h**, 2 KB above 0.74's. The structures
  then go in DOSBox-X's private area (C800h-CBFFh), which takes nothing from the upper memory
  block (it starts at CC00h either way). Both are in the configuration; every speed run below
  used them (the save loaded, the party walking).
- **`UMBPLUS.COM` changes nothing** here, as built: the chain is not 0.74's (9FFFh to D000h).
  DOSBox-X's block already starts lower (CC00h): 16 KB more than 0.74's own 128 KB, 12 KB less
  than 0.74 with UMBPLUS. The helper's needs (`UMB_NEED`, `UMB_KEPT`) are sized for D00Ah-F000h,
  so they fit, with 13 KB less spare than on 0.74.
- **The HMA.** DOSBox-X's default is `[config] dos=high, umb`: DOS itself in the HMA ("MS-DOS is
  resident in the high memory area"). Run that way (`dos_high=true`), XMS refuses the helper the
  HMA and the helper takes its other path: the far block in upper memory (`far_seg` E002h, 65,488
  bytes), which leaves no room there for the game's overlay buffer, music buffer or the
  see-through tables (`ovr_given` 0, `ghost_seg` 0): the game loses that from its 640 KB. The
  helper did not refuse and the game started, but it is the layout the helper was built to
  avoid. **`dos=umb`** leaves the HMA free as on 0.74, and the helper takes it (XMS function 01h).
- **The mouse.** DOSBox-X's defaults give the middle button to unlocking the mouse
  (`middle_unlock=manual` with `autolock=false`) and the right button to its clipboard
  (`clip_mouse_button=right`): the mod's map drag (middle button) did nothing, and `follow.py`
  stalled on it. With `autolock=true`, `autolock_feedback=none`, `middle_unlock=none`,
  `clip_mouse_button=none` the drag works (`scroll.py`: camera (1512, 240) to (1616, 192) and
  back) and the kit's clicks work as on 0.74.
- **What would have to change in the helper: nothing.** In the Loader: `UMBPLUS.COM` could learn
  DOSBox-X's chain to win back 12 KB of upper memory (not needed today).

## 4. The dice log through the file: works

`python3 -m dsloader dicelog` with `DSLOADER_MEMORY_FILE` set, no `--pid`: "Dice log attached."
It read the party and **wrote** to it at once (the Loader's own repair at attaching: "Gerakis's
Leg Armor is now counted as worn", "Chest Armor" likewise: writes to the game's item lists,
through the gate that holds the game still). `follow.py 29` from `pens-after-arena` (Kurzak's
escort) gave both speeches in the log:

```
[Portrait 5] All right, go through the door. There's a place to rest down the east hall.
[Portrait 5] I'll come get you when it's time for your next fight. If you want to fight before that, knock on the door.
```

No fight was played, so no roll was printed: the rolls come through the same ring in the far
block that the speeches' text buffer sits beside, but that is reasoning, not a test.

## 5. Writes the game acts on

- **(a) Data, a request the helper serves: acted on at once.** `qsave.py 1 DBXTEST` (the
  Loader's quick save: `SAVE_REQ` written in the helper's header, the helper calls the game's
  save routine), on `core=normal`: "done in 0.577 s", `SAVQ01.SAV` written (85,680 bytes;
  nothing had been edited in memory before it); on `core=dynamic` at 42,000 cycles, `qsave.py 2
  DYN`: "done in 0.288 s". On `core=dynamic` the dice log's own writes
  (section 4's repair), and the kit's whole way of playing (`click.py` reads the pointer;
  the save loaded and the party walked in every speed run) are data too. Data is never cached
  by a core.
- **(b) Code: at once on the normal core; on the dynamic cores the old code can run on. The same
  is true of DOSBox 0.74 today.** Three tests:
  - `codepatch.py`: the helper's `inc word [cs:main_ticks]` (its probe in the map's main loop,
    upper memory, run some 200-300 times a second) made five NOPs for 2 s, then put back;
  - `codepatch.py game`: the game's own code, conventional memory: the main loop's `INT DCh`
    (PROBE_SCROLL's site) made two NOPs, so the probe that counts isn't called;
  - `codeloop.py`: no game, a 30-byte DOS program spinning in `inc word [count] / jmp`, in
    conventional memory or loaded high: the worst case, one block of code that never leaves.

| engine, core | the helper's code (upper memory) | the game's code (conventional) | the tight loop, low and high |
|---|---|---|---|
| DOSBox-X `core=normal` | at once (191.5 passes/s, 0.0, 192.5) | (not run) | at once, both |
| DOSBox-X `core=dynamic` | **at once**, four times of four (251-287, 0.0, 283-288) | **stale**, twice of twice (287, 285.5, 287) | **stale**, both |
| DOSBox-X `core=dynamic_x86`, `dynamic_rec` | (not run) | (not run) | **stale** (`dynamic_rec` both; `dynamic_x86` low) |
| DOSBox 0.74 `core=dynamic` (the mod today, through `/proc/PID/mem`) | **stale** (291, 300.5, 298.5) | **stale** (299, 301, 300.5) | (not run) |

  - Stale means: the bytes in memory are the new ones, and the game went on running the old
    instruction for as long as watched (2 s; 6 s and more in the loop). Writing again with
    DOSBox-X stopped (SIGSTOP) changed nothing. The guest writing the same bytes over
    themselves changed nothing either (DOSBox ignores a write of the value already there).
  - So this is **not a new risk of the memory file**: writing another process's memory
    (0.74 today) bypasses DOSBox's page handlers just the same, and there the helper's code was
    stale too. The mod works on 0.74's dynamic core, so nothing it does today depends on a
    write to code that has already run being acted on. Under DOSBox-X the helper's own code
    did take the change at once on `core=dynamic`, every time; why was not found (a guess: the
    helper's variables lie among its code, and the core gives up caching pages that are written
    so often), so it is not to be relied on.
  - **What avoids it**: `core=normal` (always acted on; costs twice the host CPU, see 6); or,
    for a patch to code, have the helper make the write (a write from inside the guest goes
    through DOSBox's handlers and drops the translation: DOSBox's design, not tested here),
    the Loader only passing the bytes. No DOSBox-X setting was found that makes a dynamic core
    check memory it didn't see written.

## 6. Speed

`framerate.py 20` from `pens-after-arena`, the whole party walking, everything on, a fresh start
for every run, DOSBox-X and 0.74 in turn in one session (0.74: `core=dynamic`, as the Loader
sets it). Surface output, 320x240 window, Xvfb, no sound device.

| engine, core, cycles | frames/s | undrawn (steady pace) | walking, map units/s | steps run / lost | host CPU |
|---|---|---|---|---|---|
| 0.74 dynamic 35,000 (three runs) | 18.9, 18.9, 19.0 | 0.1, 0.1, 0.0 | 141, 143, 141 | 81 / 14 | 29%, 29%, 27% |
| 0.74 dynamic 20,000 (two runs) | 15.3, 15.6 | 3.9, 3.4 | 115, 113 | 68 / 26 | 19%, 20% |
| DOSBox-X dynamic 20,000 (two runs) | 14.2, 14.3 | 4.8, 4.8 | 115, 115 | 67 / 26 | 14%, 16% |
| DOSBox-X normal 20,000 | 13.2 | 5.6 | 115 | | 27% |
| DOSBox-X dynamic 35,000 (two runs) | 17.0, 17.1 | 1.9, 1.9 | 123, 120 | 71 / 23 | 21%, 20% |
| DOSBox-X normal 35,000 | 16.6 | 2.2 | 114 | 71 / 23 | 40% |
| DOSBox-X dynamic_rec 35,000 | 17.8 | 1.1 | 122 | | 26% |
| DOSBox-X dynamic 40,000 | 18.3 | 0.7 | 136 | 79 / 16 | 22% |
| **DOSBox-X dynamic 42,000** | **18.6** | 0.4 | **143** | **81 / 14** | 22% |
| DOSBox-X dynamic 45,000 | 18.9 | 0.1 | 151 | 85 / 11 | 25% |
| DOSBox-X dynamic_rec 45,000 | 19.0 | 0.0 | 165 | 86 / 9 | 35% |
| DOSBox-X dynamic 55,000 | 19.0 | 0.0 | 166 | 88 / 7 | 28% |
| DOSBox-X normal 55,000 | 19.0 | 0.0 | 165 | 88 / 8 | 61% |
| DOSBox-X dynamic 70,000 | 19.1 | 0.0 | 177 | 89 / 6 | 30% |

- The same cycles do less on DOSBox-X: at 35,000 it walks at about 0.74's 20,000 pace with a
  few more frames. **42,000 on `core=dynamic` gives 0.74's pace at 35,000** (the same steps run
  and lost, 143 against 141-143 map units a second, 18.6 against 18.9 frames). 20,000 walks as
  0.74's 20,000 with one frame a second fewer; about 22,000 would be the match (not run).
- The BIOS clock and the game's clock kept real time in every run (18.2 and 96 a second).
- `core=normal` gives about the same pace at the same cycles and costs about twice the host CPU
  (40% against 21% of one core here at 35,000; 61% against 28% at 55,000): affordable on a
  desktop, a cost on a Steam Deck's battery.
- `dynamic_rec` (the core an ARM Mac would use) did more per cycle than `dynamic` at 45,000
  (165 against 151): each core needs its own number.

## 7. Sound and picture, briefly

- **FluidSynth** (`mididevice=fluidsynth`, `fluid.soundfont=/usr/share/sounds/sf2/TimGM6mb.sf2`:
  Ubuntu's `timgm6mb-soundfont`, GPL-2; `fluid-soundfont-gm`'s FluidR3_GM.sf2, MIT, is installed
  too and was not played). With no sound device, FluidSynth's own driver fails ("Failed to create
  PulseAudio connection ... Can't create audio driver") and DOSBox-X falls back to no music. With
  `fluid.driver=file`: "fluidsynth: version 2.3.4", "Loaded SoundFont", "Opened
  device:fluidsynth", and `fluidsynth.wav` in the working folder: 39.8 s, 48 kHz stereo, peak
  6,535 of 32,767, a tenth of the samples above 200: the title's music, rendered through the
  soundfont. Nobody listened to it.
- **In this DOSBox-X, FluidSynth plays through its own sound driver, not DOSBox-X's mixer**:
  DOSBox-X's own capture of the same 40 s (`dx-capture /a`, a WAV in `captures=`) has no music
  in it. So the music's volume is FluidSynth's (`fluid.gain`), and a recording by DOSBox-X
  lacks it.
- **MT-32** (`mididevice=mt32`) needs the Roland ROMs, which are not free: not tried.
- **Picture** (OpenGL here is Mesa's software renderer, 4.5):
  - `output=openglpp` (pixel-perfect), `aspect=true`: a 960x720 window takes the 320x200
    picture 3x3, 960x600 (whole pixels, but not 4:3); a 1600x1200 window takes it **5x6,
    1600x1200**, whole pixels and 4:3 ("OpenGL PP: [1600x1200]: 320x200 (1.20) -> [5x6]").
    The window's size decides: the Loader would offer the sizes that are whole multiples.
  - `output=opengl`, `glshader=` a file (`contrib/glshaders/crt-lottes.glsl` from DOSBox-X's
    source, by path): "Loaded GLSL shader", and a window grab shows the scanlines and the mask.
    The built-in names are advinterp2x/3x, advmame2x/3x, rgb2x/3x, scan2x/3x, tv2x/3x, sharp;
    the CRT ones are files that DOSBox-X's packages put in its `glshaders` folder.
  - Not tried: full screen, borderless, a real graphics card, vsync.

## What was learned about the kit

- A game of its own beside the shared one needs only `PT_DISPLAY` and `PLAYTEST_WORK` now
  (`env.sh`, `paths.py`), and its pid in `$PLAYTEST_WORK/dsun.pid` (`live.py`, `framerate.py`).
- With `DSLOADER_MEMORY_FILE` exported, **every tool of the kit that goes through `live.py`
  works on the file unchanged** (state, click, scroll, follow, route, memaudit, buildcheck,
  qsave, framerate were used).
- `shot.sh` doesn't (it presses 0.74's Ctrl+F5 and looks in GOG's capture folder): `import
  -window` of the DOSBox-X window instead. DOSBox-X's window class matches `--class dosbox`.
- DOSBox-X centres its window on the screen; `start_dosboxx.sh` with `PT_SAVE` moves it to 0,0
  as `loadsave.sh` does. Without `-nomenu`/`showmenu=false` its menu bar makes the window taller.
- After a container pause every process was gone, Xvfb too, and the `/dev/shm` files with them.
- No new area was reached (the slave pens only): nothing new about water.

## Not tested

Windows and macOS (the memory file's code path differs on Windows: `CreateFileMapping`; the
Loader's `pread`/`pwrite` there, and file sharing modes, are unknown); a Flatpak or packaged
DOSBox-X (2025.01.01 or later is needed; Ubuntu 24.04 has 2024.03.01); a fight, a rest, a region
change, a long play; the Loader's window (`view`, `launch`) on the file; quick load; full
screen; sound heard by a person; MT-32; the item gate's SIGSTOP under load; Game Link; the
memory file on a disk for a long play (the system writes changed pages back to it: use tmpfs
or the temp folder).
